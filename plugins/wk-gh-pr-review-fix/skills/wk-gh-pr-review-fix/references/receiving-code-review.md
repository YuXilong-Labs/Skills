# 处理 Code Review 反馈的方法论

Code review 需要技术评估，不是情绪表演。

## 核心原则

**先核实，再实现。问清楚，再动手。技术准确性优先于社交舒适度。**

## 响应模式

```
收到 review 反馈时：

1. READ      — 读完所有反馈再反应
2. UNDERSTAND — 用自己的话复述需求（或直接问）
3. VERIFY    — 对照代码库现实核实
4. EVALUATE  — 对这个代码库是否技术可行？
5. RESPOND   — 技术确认或有理由的 pushback
6. IMPLEMENT — 逐条修改，每条测试
```

## 禁止的回应

**永远不要说：**
- "你说得对！"（无意义的认同）
- "好主意！"、"太棒了！"（表演式回应）
- "我马上实现"（没有先核实）

**应该做的：**
- 复述技术需求
- 提出澄清问题
- 有技术依据地 pushback
- 直接开始行动（行动 > 言辞）

## 反馈不清楚时

```
如果有任何不清楚的条目：
  停止 — 不要实现任何东西
  先问清楚所有不明确的条目

原因：条目之间可能有关联。局部理解 = 错误实现。
```

**例子：**
```
reviewer: "修复 1-6"
你理解 1、2、3、6；4 和 5 不清楚。

❌ 错误：先实现 1、2、3、6，再问 4、5
✅ 正确："我理解 1、2、3、6。在继续之前需要澄清 4 和 5。"
```

## 按来源区分处理方式

### 来自合作方（trusted）
- 理解后实现
- 范围不清楚时仍然要问
- 不做表演式认同
- 直接行动或技术确认

### 来自外部 reviewer

在实现之前检查：
1. 对这个代码库技术上是否正确？
2. 是否会破坏现有功能？
3. 当前实现是否有特定原因？
4. 是否兼容所有支持的 iOS 版本？
5. reviewer 是否了解完整上下文？

如果建议有误 → 以技术理由 pushback

如果无法轻易核实 → 直说："我需要 [X] 才能核实这个。要我 [调查/询问/直接做]？"

如果与已有架构决策冲突 → 停下来和合作方确认

## YAGNI 检查

```
如果 reviewer 建议"按规范实现某功能"：
  在代码库中 grep 这个功能的实际调用

  如果没有调用：告知 reviewer "这个端点没有被调用，YAGNI？"
  如果有调用：再按建议实现
```

## 实现顺序

```
多条反馈时：
  1. 先澄清所有不清楚的条目
  2. 按以下顺序实现：
     - 阻塞性问题（崩溃、安全）
     - 简单修复（拼写、import）
     - 复杂修复（重构、逻辑）
  3. 每条分别测试
  4. 验证无回归
```

## 何时 Pushback

遇到以下情况应该 pushback：
- 建议会破坏现有功能
- Reviewer 没有完整上下文
- 违反 YAGNI（未使用的功能）
- 对当前技术栈技术上不正确
- 存在遗留/兼容性原因
- 与架构决策冲突

**如何 pushback：**
- 使用技术理由，不防御
- 提具体问题
- 引用可工作的测试/代码
- 架构级别的问题需要合作方参与

## 正确反馈时的回应

```
✅ "已修复。[简短描述改了什么]"
✅ "发现了 — [具体问题]。已修复在 [位置]。"
✅ [直接修改代码，展示结果]

❌ "你说得对！"
❌ "好发现！"
❌ "谢谢指出！"
❌ 任何感谢表达
```

原因：行动证明一切。代码本身就说明你听到了反馈。

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 表演式认同 | 复述需求或直接行动 |
| 盲目实现 | 先对照代码库核实 |
| 批量不测 | 逐条实现，每条测试 |
| 假定 reviewer 正确 | 检查是否破坏现有功能 |
| 回避 pushback | 技术准确性 > 舒适度 |
| 部分实现 | 先澄清所有条目 |
| 无法核实仍继续 | 说明限制，寻求指引 |

## GitHub 线程回复

回复 inline review comment 时，必须在原线程内回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），**不能**用顶层 PR comment 代替。
